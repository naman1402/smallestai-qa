## NEW failures or anomalies

- **No new API failures.** All 27 non-slow tests gave the same outcome in all 3 runs, and every outcome matched the expectations except R6, which didn't trigger. The feature-conformance re-runs' A1 ("one-shot WS never sent `complete`") wasn't seen: all 6 raw WS streams and all 3 `underrun-ws` streams got `complete`.
- **Write-up error (ours), R1:** `b0f12194-d873-41d4-8442-0285be9acafa` is the resume reply, not a late reply segment. See the correction under R1.
- **Observation (not a failure):** time to first audio was clearly lower than in the first session on all transports (HTTP median 579 vs 1286 ms, SSE 224 vs 277, WS 137 vs 206). The first-session TTFA numbers and R6 may both reflect server load at about 18:30 IST. That can't be proven from this data.
- **Observation, R1 (consistent in 3/3, not new behaviour):** after a cancel, the only non-audio frame is a `complete` for the second reply segment, about 4 s after its last chunk (R5 backoff), although the context was still open. A client could mistake it for a cancel ack. It isn't one: it arrives about 6 s after the cancel.

## Caveats

- **R1 "buffered fragment not spoken"** is inferred from segment count and durations. No audio content was checked.
- **R1 resume segment:** the test closes the socket at the resume segment's first chunk, so that segment's duration is a test artifact.
- **R1 `quiet(4.5)`:** it waited until about 11 s because the late `complete` frame reset the quiet timer. This doesn't affect the R1 values.
- **R6 gap scoring:** the extra WS samples are timed from `send()` with a plain client. `underrun()` uses only relative chunk times, so the scoring is the same as the test's.
- **Sample size:** all 3 runs fell within about 17 minutes, from one client location.
