- **What this file is:** the branded voice support agent (`src/smallest_qa/app/`) was driven end to end by
  `tests/e2e/test_support_agent.py`, 3 complete times, and the scorecards were compared check by check.

## New from the prototype

| Item | Rate | What happens | Status |
|---|---|---|---|
| WebSocket ignores `output_format: "ulaw"` | 3/3 | ulaw/pcm byte ratio 0.99 / 1.05 / 0.94: the socket returns PCM with no error. The streaming guide lists `ulaw` for the WebSocket (`streaming.md` line 373); only the WebSocket API schema omits `output_format`. REST serves ulaw as documented | Reported as **E1** (Medium). Workaround: request 8 kHz PCM and encode G.711 locally (the phone leg then had 0 late frames in every run) |
| Mid-sentence stall early in a turn | 2 of 42 turns (stall census below), both in run 1 | Turn 0: 0.22 s of audio, then **547 ms** of nothing although the whole sentence had been sent; a 150 ms jitter buffer runs dry for 0.18 s (`7eda87b9-…`, turn summary `5b34f7f5-d3cf-44e4-a8ed-d4cd88f51a95`). A second 592 ms stall (busy hour) did not cause a gap | Intermittent, same family as R6. Not permanent |
| Short opening sentence delays first audio | 6/6 occurrences | Replies opening with "Of course." get first audio ~500–710 ms after the first fragment, vs ~170–400 ms for others: the server holds a sentence until it is "long enough" | **Documented** (continuations, "How buffering works" rule 2). Product tuning, not a bug: lower `max_buffer_delay_ms` or avoid very short first sentences |
